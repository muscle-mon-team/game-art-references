# 레퍼런스를 게임에 적용하는 방법

이 안내는 자료를 찾은 뒤 다른 LLM이나 작업자가 실제 게임의 적용안과 구현 인수인계를 만들 때 사용합니다. [수집 지침](../CONTRIBUTING.md)은 자료를 늘리는 방법을, 이 문서는 그 자료를 근거로 디자인을 구체화하는 방법을 다룹니다.

이 저장소에서 분석 문서와 제안은 작성할 수 있습니다. 실제 게임 파일을 바꾸려면 대상 저장소와 변경 범위가 승인되어 있어야 합니다. 현재 사용자의 스타일은 아직 선택되지 않았고, 예시 문서도 선택을 대신하지 않습니다.

## 먼저 읽을 순서

| 작업 | 읽을 문서 |
| --- | --- |
| 후보를 찾고 실제 장면을 비교 | 이 문서의 1~3단계, [수집 지침](../CONTRIBUTING.md) |
| 스타일을 제안하고 선택받기 | 4~5단계, [스타일 정리 양식](templates/STYLE_BRIEF.md), [작성 예시](examples/TOY_STAGE_PROPOSAL.md) |
| 승인된 디자인 구현을 맡기기 | 6~7단계, [구현 인수인계 양식](templates/IMPLEMENTATION_HANDOFF.md) |
| Muscle Mon의 Godot 코드와 연결 | [Godot 인수인계 안내](GODOT_HANDOFF.md)와 대상 게임 저장소의 최신 지침 |

## 1. 지금 맡은 작업을 구분

시작할 때 아래 내용을 기록합니다. 기존 대화에서 확정된 내용은 재사용하고 다시 묻지 않습니다.

- 작업 종류: 자료 수집 / 스타일 조사 / 적용안 제안 / 승인된 디자인 구현
- 수정할 저장소와 경로, 읽기만 할 저장소
- 대상 게임의 현재 요구, 카메라와 이동 규칙, 지원 플랫폼
- 사용자에게 확인된 리소스와 제작 여건
- 파일 수정, 커밋, push와 배포를 허용받은 범위
- 아직 선택되지 않은 디자인과 정책

레퍼런스 저장소에서 자료를 추가하라는 지시를 실제 게임 저장소 수정 승인으로 확대하지 않습니다. 목표나 리소스 확보 여부가 불명확하면 해당 결정에 의존하는 작업만 멈추고 확인합니다.

## 2. 카탈로그에서 장면 선택

웹의 검색과 차원, 스타일 필터를 활용하거나 `data/catalog.json`을 읽습니다. 처음에는 목적이 다른 대표 장면 몇 장을 비교하고, 필요한 부분만 추가로 찾는 것이 좋습니다. 유명한 작품 전체를 이름만 나열하지 않습니다.

아래는 저장소 루트에서 실행하는 읽기 전용 검색 예시입니다. 전체 카탈로그를 LLM의 입력에 그대로 넣는 대신 필요한 필드를 좁혀 읽을 수 있습니다.

```sh
python3 - <<'PY'
import json
from pathlib import Path

data = json.loads(Path('data/catalog.json').read_text())
selected = [g for g in data['games']
            if g['dimension'] == '2.5D' and '토이' in g['tags']]
for game in selected[:6]:
    print(json.dumps({
        'gameId': game['id'], 'title': game['title'],
        'camera': game['camera'], 'note': game['note'],
        'screenshots': game['screenshots'][:2]
    }, ensure_ascii=False))
PY
```

각 장면에는 다음 근거를 남깁니다.

| 항목 | 기록할 값 |
| --- | --- |
| 게임과 장면 | `game.id`, `shot.id`, 게임 이름 |
| 원본 | `shot.full`, `shot.source` |
| 탐색 링크 | `https://muscle-mon-team.github.io/game-art-references/#game=<game.id>` |
| 자료 버전 | 카탈로그가 들어 있는 Git 커밋 SHA와 확인 날짜 |
| 장면 종류 | 실제 플레이 / 컷신 / 스토어 소개 이미지 등 직접 확인한 종류 |
| 확인 범위 | 실제로 연 원본과 해상도, 확인하지 못한 부분 |

현재 갤러리는 게임별 링크만 지원합니다. `#shot=...` 같은 개별 이미지 링크를 만들지 말고 이미지 ID와 원본 URL을 함께 전달합니다. `collectedOn`은 자동 갱신 시각이 아니므로 그것만으로 자료 버전을 판단하지 않습니다.

### 즐겨찾기를 넘겨받았다면

내보낸 선택 JSON은 주로 `favorites`의 이미지 ID와 `notes`를 담습니다. 이미지 URL, 출처, 카탈로그 커밋은 들어 있지 않습니다. 같은 시점의 카탈로그와 결합해 참조 표를 작성합니다.

아래 예시는 사용자에게 받은 파일을 `.local/my-selection.json`에 둔 경우입니다. 저장 위치가 다르면 실제 경로를 사용합니다. 선택 파일은 개인 자료이므로 원격 저장소에 올리지 않습니다.

```sh
python3 - <<'PY'
import json
from pathlib import Path

catalog = json.loads(Path('data/catalog.json').read_text())
board = json.loads(Path('.local/my-selection.json').read_text())
index = {s['id']: (g, s) for g in catalog['games'] for s in g['screenshots']}
missing = [image_id for image_id in board['favorites'] if image_id not in index]
if missing:
    raise SystemExit('현재 카탈로그에서 찾지 못한 이미지 ID: ' + ', '.join(missing))
for image_id in board['favorites']:
    game, shot = index[image_id]
    print(json.dumps({
        'gameId': game['id'], 'title': game['title'], 'imageId': image_id,
        'full': shot['full'], 'source': shot['source'],
        'userNote': board.get('notes', {}).get(image_id, '')
    }, ensure_ascii=False))
PY
```

없는 이미지 ID를 다른 이미지나 배열의 같은 순번으로 대체하지 않습니다. 원래 카탈로그 버전을 확보하거나 사용자와 참조 대상을 다시 확인합니다. 좋아요와 메모는 관심 표현이며 디자인 확정의 근거로 자동 해석하지 않습니다.

## 3. 원본을 직접 보고 관찰

게임 이름과 태그, HTTP 정상 응답을 본 것만으로 시각 분석을 완료하지 않습니다. 실제 이미지를 열고 같은 기준으로 비교합니다. 수동 자료의 `kind`, `contentVerified`, `contentReviewNote`는 `data/console-sources.json`에서 확인할 수 있으며 현재 웹용 카탈로그에는 전달되지 않습니다.

이미지를 직접 볼 수 없는 LLM이나 실행 환경에서는 그 한계를 밝히고 시각 검수를 수행할 수 있는 도구 또는 담당자에게 확인을 요청합니다. 파일을 받았거나 URL을 읽었다는 사실을 이미지 내용 확인으로 보고하지 않습니다.

| 관찰 항목 | 기록할 내용 |
| --- | --- |
| 색과 명암 | 배경, 캐릭터, 적과 효과의 색 역할 및 밝기 차이 |
| 형태와 비례 | 큰 덩어리, 실루엣, 모서리, 인물과 소품의 상대 크기 |
| 재질 | 화면에서 보이는 무광, 광택, 종이 단면, 섬유 등의 표현 |
| 조명 | 밝은 면과 그림자 방향, 그림자의 경계, 배경과 인물의 분리 |
| 카메라와 깊이 | 보이는 면, 겹침, 전경과 배경의 밀도. 이동 규칙은 별도 확인 |
| 전투 시인성 | 탄환, 적, 바닥과 폭발의 구별. 관련 장면이 없으면 미확인 |
| 움직임과 리듬 | 정지 화면에서는 확인 불가. 공식 영상 등을 실제로 확인한 경우에만 근거 기록 |

다음 셋을 항상 분리합니다.

1. **관찰 사실:** 해당 화면에서 실제로 보이는 것
2. **적용 제안:** 그 효과를 우리 게임에서 만들기 위한 선택과 수치
3. **미확인:** 이미지로 알 수 없거나 직접 확인하지 못한 것

스크린샷만으로 원작의 엔진, 실제 셰이더 값, 모델의 폴리곤 수, 리깅 방식, 후처리 종류, 성능 비용을 단정하지 않습니다. 화면에서 색을 추출하더라도 조명과 후처리가 반영된 표시 색이며, 원작 재질의 albedo 값이라는 뜻은 아닙니다.

스토어 소개 이미지는 실제 화면 위에 문구, 장식, 별도 캐릭터와 기기 프레임이 합성되어 있을 수 있습니다. 그런 요소를 실제 플레이 HUD나 카메라 구도로 옮기지 않습니다.

## 4. 우리 게임의 규칙으로 바꾸기

[스타일 정리 양식](templates/STYLE_BRIEF.md)에 적용안을 작성합니다. 기준이 되는 레퍼런스와 보조로 참고할 항목을 정하고, 여러 작품의 특징을 이유 없이 전부 섞지 않습니다.

각 제안에는 원본 장면, 참고한 특징, 우리 게임에서의 구체적인 규칙, 적용 후보 위치, 제작 재료, 확인 방법을 붙입니다. 예를 들어 “귀엽게”만 적기보다 “배경의 작은 무늬를 줄이고 캐릭터와 탄환 실루엣이 먼저 읽히도록 한다”처럼 결과를 설명합니다.

### 디자이너와 3D 모델링 담당자가 없는 현재 조건

- 기존 모델과 소품을 사용할 수 있는지 실제 리소스를 확인합니다. 현재 디자인이 불만족스럽다는 사용자 맥락을 보존하고 기존 외형의 유지를 자동 전제로 삼지 않습니다.
- 단순한 도형 조립, 기존 재질 조정, 완성형 에셋 활용을 비교합니다. 완성형 에셋도 구매, 리깅, 애니메이션, 포맷, 상업 이용 조건과 수정 필요 여부를 확인해야 합니다.
- 새 캐릭터와 맞춤 애니메이션이 필요한 항목은 확보 경로와 제작 부담을 명시합니다. 확보하지 않은 모델을 있다고 쓰거나, AI 생성만으로 품질과 일관성이 보장된다고 안내하지 않습니다.
- 구매나 유료 도구 가입은 별도 행동입니다. 스타일 제안 승인으로 결제와 외부 계정 변경을 진행하지 않습니다.
- 어려운 리소스가 있으면 가능한 작은 적용안과 필요한 외부 제작을 구분해 제안합니다. 불가능한 부분을 숨겨 전체 구현을 약속하지 않습니다.

Godot 4, 고정 측면 뷰, Z=0 전투면은 이 프로젝트의 사용자 제공 맥락입니다. 실제 구현을 시작할 때 최신 기획과 코드에서 재확인합니다. 참조 게임이 3D라고 카메라나 이동축을 바꿀 근거로 사용하지 않습니다.

## 5. 사용자 결정과 승인 상태 기록

상태를 `후보`, `사용자 확정`, `구현 완료`, `대상 환경 검증`으로 구분합니다. 확정 기록에는 날짜, 실제 발언 또는 결정 문서, 승인한 규칙과 파일 또는 기능 범위를 남깁니다.

스타일 선택과 실제 게임 코드 수정, 원격 반영, 배포의 승인은 각각 범위를 대조합니다. 이미 받은 승인은 다시 묻지 않으며, 새로 발견한 디자인 또는 정책 결정은 필요한 부분만 확인합니다. 무응답과 다른 에이전트의 추천은 승인으로 처리하지 않습니다.

## 6. 작은 첫 화면과 구현 인수인계

첫 구현은 한 화면의 캐릭터, 바닥, 소품 몇 개, 적 하나와 탄환처럼 비교할 수 있는 작은 범위로 제안합니다. 정확한 대상과 완료 기준은 사용자가 선택한 스타일과 실제 게임의 구조에 맞춥니다. 장면 크기나 리소스 수를 모든 작업에 고정 적용하지 않습니다.

승인된 내용은 [구현 인수인계 양식](templates/IMPLEMENTATION_HANDOFF.md)에 기록합니다. 대상 저장소의 최신 AGENTS, 가까운 문서와 코드, 실제 상태와 호출 흐름을 확인한 뒤 변경 위치를 고릅니다. 이 저장소의 지침이 대상 게임의 실행 계약을 대신하지 않습니다.

형태와 색을 바꾸는 작업이 HP, 충돌, 공격 허용과 저장 규칙까지 바꾸는지 확인합니다. 단순 외형 변경을 근거로 게임 규칙을 임의로 바꾸지 않습니다. 캐릭터나 로고, 모델과 텍스처의 복제가 아니라 확인한 표현 원리를 독자적인 내용에 적용합니다.

## 7. 구현 후 근거 남기기

구현은 승인된 대상 저장소의 검증 규칙을 따릅니다. 로컬 렌더 성공, 조작 확인, 실기기 성능과 원격 배포는 서로 다른 상태입니다. 새로 만든 정지 이미지나 AI 시안을 실제 게임 실행 화면으로 제시하지 않습니다.

변경 전후를 같은 카메라, 해상도와 가능한 같은 장면에서 비교하고, 각 스타일 규칙이 어떻게 반영됐는지 기록합니다. 무엇을 실행했고 무엇이 미검증인지, 예상보다 비싼 효과나 미확보 리소스가 남았는지 설명합니다. 아직 선택되지 않은 디자인을 구현 완료 상태로 바꾸지 않습니다.
